# Windows Testing Guide

This guide covers local Windows testing for Oinkoin before relying on the GitHub release runner.

## 1. Required tools

Use a Windows 10 or Windows 11 x64 machine with:

- Git
- Flutter stable
- Visual Studio 2022 with **Desktop development with C++** installed
- A Windows 10/11 SDK selected in Visual Studio
- Inno Setup 6 (only required for building the installer)

Verify the Flutter and Windows toolchain before testing:

```powershell
flutter --version
flutter doctor -v
flutter config --enable-windows-desktop
```

`flutter doctor -v` should report Windows desktop support without a required-tool error.

## 2. Check out the Windows branch

Clone the branch with its Flutter submodule:

```powershell
git clone --branch windows-support --recurse-submodules https://github.com/emavgl/oinkoin.git
cd oinkoin
git submodule update --init --recursive
```

The committed `windows/` directory is the application runner. Do **not** run `flutter create` for this branch.

The GitHub workflow uses the Flutter submodule's stable branch. If you want to reproduce that exact SDK locally and have not configured `flutter` globally, use:

```powershell
git -C submodules/flutter checkout stable
git -C submodules/flutter pull origin stable
.\submodules\flutter\bin\flutter.bat config --enable-windows-desktop
.\submodules\flutter\bin\flutter.bat pub get
```

Otherwise, use a current Flutter stable installation from your `PATH` for the commands below.

## 3. Test the app in debug mode

From the repository root:

```powershell
flutter pub get
flutter analyze
flutter test
flutter run -d windows
```

Leave the app running long enough to exercise the normal flows, then stop it with `q` in the Flutter terminal.

### Windows behavior checklist

Verify the following Windows-specific behavior:

- The application opens and closes without errors.
- Data can be created, edited, deleted, and is still present after restarting the app.
- SQLite initializes successfully and the database remains writable.
- Backup creation and restore work from the Windows file locations.
- Save dialogs appear when exporting files.
- Website, email, and contributor links open through the Windows default application.
- The local timezone is detected correctly.
- The desktop authentication bypass works; no mobile biometric prompt is shown.
- The UI remains usable when resizing the native window.

## 4. Build and test the release bundle

Build the same architecture used by the release workflow:

```powershell
flutter pub get
flutter build windows --release
```

The x64 release directory is:

```text
build\windows\x64\runner\Release
```

Confirm that it contains at least:

- `piggybank.exe`
- `flutter_windows.dll`
- the `data` directory
- the native plugin DLLs generated by the build

Run the release executable directly:

```powershell
& .\build\windows\x64\runner\Release\piggybank.exe
```

Repeat the Windows behavior checklist against this release build, not only the debug build.

## 5. Include the Visual C++ runtime for distribution

A self-contained ZIP or installer should include the Visual C++ runtime DLLs. Run this from the repository root after building:

```powershell
$releaseDir = "build\windows\x64\runner\Release"
foreach ($dll in @("msvcp140.dll", "vcruntime140.dll", "vcruntime140_1.dll")) {
    $source = Join-Path (Join-Path $env:WINDIR "System32") $dll
    if (-not (Test-Path $source)) {
        throw "Required Visual C++ runtime was not found: $source"
    }
    Copy-Item -Path $source -Destination $releaseDir -Force
}
```

Create and test the portable ZIP if desired:

```powershell
Compress-Archive `
    -Path build\windows\x64\runner\Release\* `
    -DestinationPath piggybank-windows-x64.zip
```

Extract the ZIP to a directory that is not the build directory and launch `piggybank.exe` from the extracted directory. This helps catch missing runtime or bundled-DLL problems.

## 6. Build and test the Inno Setup installer

Install Inno Setup 6, then compile the installer from the repository root. Replace the version with the release version being tested:

```powershell
$compiler = Join-Path (Join-Path ${env:ProgramFiles(x86)} "Inno Setup 6") "ISCC.exe"
& $compiler "/DAppVersion=1.10.0" windows\installer.iss
```

The installer is written to:

```text
build\windows\installer\oinkoin-windows-x64-setup.exe
```

Test the installer on the Windows machine:

1. Run the setup executable.
2. Install using the default location.
3. Launch Oinkoin from the Start Menu and, if selected, the desktop shortcut.
4. Repeat the Windows behavior checklist using the installed application.
5. Close the app and launch it again to verify data persistence.
6. Uninstall it from Windows Settings or **Add or remove programs**.
7. Confirm that the application files and shortcuts are removed while user data is not unintentionally deleted.

For stronger validation, test the installer on a clean Windows virtual machine or Windows Sandbox without Visual Studio or Flutter installed.

## 7. Validate the GitHub release runner

The release workflow is in `.github/workflows/on-release.yml` and currently triggers on a released GitHub release. It also performs the existing Android build, version bump, tag update, and publishing jobs, so do **not** create a real release only to test the Windows job.

Before enabling or relying on the release runner, confirm locally that:

- `flutter analyze` passes.
- `flutter test` passes.
- `flutter build windows --release` succeeds.
- The release executable launches from outside the build directory.
- The ZIP works after extraction.
- The Inno Setup installer installs, launches, and uninstalls successfully.
- The release checkout contains the committed `windows/` runner and does not need `flutter create`.

Once those checks pass, the Windows release job will:

1. Check out `master` after the version bump.
2. Update the Flutter submodule to stable.
3. Enable Windows desktop support.
4. Run `flutter pub get`.
5. Build the x64 Windows release.
6. Add the Visual C++ runtime DLLs.
7. Produce the portable ZIP and Inno Setup installer.
8. Upload both files to the GitHub release.

The Windows runner cannot be fully compiled on Linux, so the final confirmation must come from a local Windows build or a controlled Windows CI run.
