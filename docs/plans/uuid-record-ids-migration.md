# Plan: UUID record IDs

Status: **proposed** (not implemented)
Related: issue #452 (backup restore dropped identical records), fixed in 1.16.2 by
making the content-based dedupe one-to-one (`addRecordsInBatch`).
Owner: TBD

## 1. Why

Records are identified by an `INTEGER PRIMARY KEY AUTOINCREMENT`. That id is
**database-local**, so it is discarded by the backup/restore path
(`addRecordsInBatch` sets `record.id = null`) and `_obackup.json` files carry ids
that only mean something inside the database they were exported from.

Because ids are not portable, "does this record already exist?" cannot be
answered by identity and must be answered by **comparing content**: amount,
datetime, title, category, wallet, description. Content is not identity:

* Two identical expenses bought at the same minute are legal and must coexist
  (issue #452) — the 1.16.2 one-to-one matching works around this, but the check
  is still fuzzy and expensive:
  * each import row runs a `SELECT COUNT(*)` over a table with **no indexes**,
    i.e. O(n·m) on a large restore;
  * records that were created independently on two devices and only *look* alike
    are silently merged on restore;
* tag associations have no stable target, so they must be resolved by re-querying
  the record by its fields (`addRecordsInBatchNoDuplicateCheck`, used by the CSV
  importer, still does this and can attach tags to the wrong identical twin).

With a UUID, "same record" becomes decidable:

* restore/merge is `INSERT OR IGNORE` on the primary key — exact, indexed and
  idempotent;
* identical-looking records are distinct because their ids differ;
* `records_tags.record_id` points at a real record in both DB and backup, so no
  field lookup is needed anywhere;
* the fuzzy checks in `addRecordsInBatch` can be deleted for current backups and
  kept only as a legacy path.

## 2. Goals / non-goals

Goals

1. `records.id` becomes a UUID (`TEXT`), generated by the app, preserved across
   backup/export/restore.
2. Restoring a backup on top of newer data keeps working: records already present
   are skipped **by id**, not by content.
3. Old (integer-id) backups still import correctly.
4. No regression in record ordering, selection, editing, duplicating, deleting,
   CSV import, recurrent records, budgets or the home widget.

Non-goals (possible follow-ups, not in this change)

* UUIDs for `wallets`, `profiles`, `categories`, `budgets`. Note that wallets have
  the same class of problem today (restore matches wallets by name/default flag),
  so this is a candidate for a later change.
* Any sync / multi-device merge feature.
* Changing the backup envelope format beyond the `records` / `record_tag_associations`
  id representation.

## 3. Target design

### 3.1 Schema (v34)

```sql
CREATE TABLE records (
    id          TEXT PRIMARY KEY,          -- uuid v4, generated by the app
    datetime    INTEGER,
    timezone    TEXT,
    value       REAL,
    title       TEXT,
    description TEXT,
    category_name TEXT,
    category_type INTEGER,
    recurrence_id TEXT,
    wallet_id   INTEGER,
    transfer_wallet_id INTEGER,
    transfer_value REAL,
    profile_id  INTEGER
);

CREATE TABLE records_tags (
    record_id TEXT NOT NULL,
    tag_name  TEXT NOT NULL,
    PRIMARY KEY (record_id, tag_name)
);
```

* `records` stays a rowid table (no `WITHOUT ROWID`), so the hidden `rowid`
  remains a monotonic insertion counter and can replace the current
  `ORDER BY … id DESC` tie-breaks without adding a column (see §3.4).
* No `AUTOINCREMENT`, no `INTEGER` affinity on `id`: inserting a uuid string must
  not be coerced.
* Triggers (`update_category_usage`, `update_category_usage_on_update`,
  `update_category_usage_on_delete`, `delete_record_tags`) only reference
  `NEW.id` / `OLD.id`, so their bodies are unchanged — but they must be recreated
  after the table rebuild (dropping a table drops its triggers).

### 3.2 Model and API types

| Surface | Today | After |
| --- | --- | --- |
| `Record.id` | `int?` | `String?` |
| `Record.fromMap` / `toMap` | `map['id']` int | `map['id']` String |
| `RecordTagAssociation.recordId` | `int` | `String` |
| `DatabaseInterface.addRecord` | `Future<int>` | `Future<String>` |
| `getRecordById` | `int id` | `String id` |
| `deleteRecordById` | `int? id` | `String? id` |
| `deleteRecordsInBatch` | `List<int>` | `List<String>` |
| `duplicateRecordsInBatch` | `List<int>` | `List<String>` |
| `updateRecordById` | `int? recordId` | `String? recordId` |
| `updateRecordWalletInBatch` | `List<int> ids` | `List<String> ids` |
| UI selection | `Set<int> _selectedRecordIds` | `Set<String>` |

UUID generation follows the existing convention for
`recurrent_record_patterns` (`lib/services/database/sqlite-database.dart`,
`Uuid().v4()`), and is done in `addRecord` / `addRecordsInBatch` when
`record.id == null`. `id == null` keeps meaning "not persisted yet" for the UI
(`edit-record-page.dart` relies on it).

### 3.3 Backup format and merge semantics

`Backup.toMap` already writes `records[].id`; after the change it writes a uuid
string. `record_tag_associations[].record_id` matches it directly.

Import rules, decided by the **type of the id found in the file** (more robust
than relying on `database_version`, which is a string in old backups):

| Backup id | Behaviour on import |
| --- | --- |
| `String` (uuid) | Keep the id, insert with `INSERT OR IGNORE`. Records already in the DB are skipped by primary key; records that merely look identical are kept. No content matching. |
| `int` (legacy, `database_version` ≤ 33) | Generate a new uuid per record. Keep the 1.16.2 one-to-one content check as the dedupe fallback (it is the only option for id-less records), and build `backup int id → new uuid` to remap `record_tag_associations`. |
| absent | Generate a new uuid; no dedupe (legacy edge case: old files without ids). |

Also required:

* `BackupService.importDataFromBackupFile` currently drops ids implicitly via
  `addRecordsInBatch`; add an explicit "preserve ids" flag or a dedicated
  `addRecordsInBatchPreservingIds` so CSV import keeps generating new ids.
* `recordIdToTags` map in `BackupService` becomes `<String, Set<String>>` for
  current backups, with the int→uuid remap for legacy ones.
* Wallet/profile remapping stays as-is (records still get remapped
  `wallet_id` / `profile_id`).

### 3.4 Ordering

Two places use the integer id as an insertion-order tie-break:

* `SqliteDatabase.getLatestMainCurrencyTransferRates`:
  `ORDER BY r.datetime DESC, r.id DESC`
* `records-utility-functions.dart` (`groupRecordsByDay` sort):
  `(b.id ?? 0).compareTo(a.id ?? 0)`

Both must switch to insertion order (`ORDER BY r.datetime DESC, r.rowid DESC`,
and a `rowid` exposed as e.g. `record_order`/`created_at` when sorting in Dart),
because uuids are not monotonic. The migration copies rows in ascending old id
order so rowids keep matching the previous creation order.

### 3.5 Other surfaces to audit

* `getMatchingRecord(Record?)` — content lookup used by CSV/import paths; keep,
  but document it is content-based.
* `addRecordsInBatchNoDuplicateCheck` (CSV import) — replace its "find the record
  by fields to attach tags" step with the id returned by the insert; this also
  fixes tag attachment for identical twins in CSV imports.
* `csv-service.dart` — no ids are exported; nothing to change.
* `records-page.dart`, `records-day-list.dart`, `records-per-day-card.dart` —
  `Set<int>` → `Set<String>`.
* Home widget / budget / statistics code uses wallet and budget ids only —
  untouched.

## 4. Phased implementation

### Phase 0 — audit (0.5 day)

* `grep -rn "int? id\|int id\|\.id!\|getRecordById\|deleteRecordById\|deleteRecordsInBatch\|duplicateRecordsInBatch\|updateRecordById\|updateRecordWalletInBatch" lib/` and record every hit in a checklist on this issue/PR.
* Confirm no other table references `records.id` besides `records_tags`.

### Phase 1 — model + interface (0.5 day)

1. `lib/models/record.dart`: `String? id`, `fromMap`/`toMap`.
2. `lib/models/record-tag-association.dart`: `String recordId`.
3. `lib/services/database/database-interface.dart`: signatures per §3.2.
4. Regenerate mocks (`flutter pub run build_runner build`), update
   `test/backup/*.mocks.dart`.

### Phase 2 — schema v34 (1 day)

1. `SqliteDatabase.version` 33 → **34**.
2. `_createRecordsTable` / `_createRecordsTagsTable` use TEXT ids (fresh installs).
3. `_migrateTo34` in `SqliteMigrationService`:
   1. inside a single transaction;
   2. read `SELECT id FROM records ORDER BY id`, generate a uuid per row in Dart
      (chunked, e.g. 5 000 ids per statement) into a temp table
      `records_id_map(old_id INTEGER PRIMARY KEY, new_id TEXT NOT NULL)`;
   3. `CREATE TABLE records_new (id TEXT PRIMARY KEY, …)` and
      `INSERT INTO records_new SELECT m.new_id, r.datetime, … FROM records r JOIN records_id_map m ON m.old_id = r.id ORDER BY r.id`
      (ascending old id ⇒ rowid order preserved);
   4. `CREATE TABLE records_tags_new (record_id TEXT NOT NULL, tag_name TEXT NOT NULL, PRIMARY KEY (record_id, tag_name))` and copy via the map;
   5. drop old tables, rename, recreate the four triggers;
   6. verify `COUNT(*)` of records and tag associations before/after and roll back
      on mismatch;
   7. drop `records_id_map`.
4. Register `_migrateTo34` in `migrationFunctions`.
5. Make sure the migration is safe if the database file is copied (automatic
   database copy) mid-upgrade: the migration runs before any read.

### Phase 3 — database layer (1 day)

* `addRecord`: `record.id ??= Uuid().v4()`, insert with the map containing `id`,
  return `String`.
* `addRecordsInBatch`: assign uuids, insert with `INSERT OR IGNORE` (see §5 for
  the legacy flag), keep one transaction + per-insert id for tags.
* `getRecordById`, `updateRecordById`, `deleteRecordById`,
  `deleteRecordsInBatch`, `duplicateRecordsInBatch`,
  `updateRecordWalletInBatch`: `String` ids.
* `duplicateRecordsInBatch`: clear `id` on the copy so a new uuid is generated.
* Ordering fixes from §3.4.

### Phase 4 — backup import/export (1 day)

* `addRecordsInBatch` gains `{bool preserveIds = false}` (or a separate method):
  * `preserveIds: true` + uuid id ⇒ insert with that id, `INSERT OR IGNORE`;
  * `preserveIds: true` + int/absent id ⇒ legacy path: generate uuid + 1.16.2
    one-to-one content check.
* `BackupService.importDataFromBackupFile`:
  * detect legacy backups (`id is int`);
  * build `oldRecordId → newUuid` and remap `record_tag_associations`;
  * attach tags through the per-insert id (already the case in 1.16.2).
* `_countDuplicateRecords` / `_duplicateSignature` stay, but only reachable from
  the legacy path.
* Update `Backup` doc/comments and the `database_version` written by
  `createJsonBackupFile` (it uses `SqliteDatabase.version`, so it becomes `34`).

### Phase 5 — UI + CSV (0.5 day)

* `Set<int>` → `Set<String>` in records selection widgets.
* `addRecordsInBatchNoDuplicateCheck`: attach tags by inserted id (§3.5).
* Grep for `int` casts of record ids in the UI and `as int` on `map['id']`.

New tests:

* restore of a uuid backup is idempotent: importing twice adds no records;

* legacy int-id backup still restores with the 1.16.2 one-to-one behaviour;
* CSV import of two identical rows attaches each row's tags to its own record.

## 5. Compatibility matrix

| Backup → App | 1.16.x (int ids) | ≥ 1.17.0 (uuid ids) |
| --- | --- | --- |
| Backup made by 1.16.x (int ids) | works | works (legacy path: uuid generated + one-to-one content dedupe) |
| Backup made by ≥ 1.17.0 (uuid ids) | **fails** (`TEXT` id into `INTEGER PRIMARY KEY` → datatype mismatch, or `map['id'] as int` throws) | works |

Mitigations for the "new backup on old app" case:

* document it in the release notes and the in-app backup screen copy if we want
  (a new string ⇒ translation cost — evaluate reusing an existing string);
* optionally have old paths fail gracefully: the restore already returns `false`
  and shows "Make sure you have the latest version of the app…", which is an
  acceptable message for this case.

Database downgrade (install 1.16.x after the DB was migrated to 34) is **not**
supported: old code reads `map['id'] as int` and will throw. Users recovering from
that need a fresh install + restore of a pre-migration backup. Mention it in the
release notes.

## 6. Risks and mitigations

| Risk | Mitigation |
| --- | --- |
| Migration corrupts records / loses tags | single transaction + before/after count assertions + rollback on mismatch; dedicated migration tests on a real v33 fixture |
| Large DB migration is slow / OOM | chunked id map (5 000), set-based `INSERT … SELECT`, no per-row Dart copy |
| Migration runs twice / partially | `onUpgrade` version gate; all steps use `IF NOT EXISTS`, and the final rename is the last step |
| Uuid inserted but `id` still stored as number somewhere | grep for `as int` on ids; type the model as `String?` so the analyzer catches it |
| Ordering regressions (bank-like lists, currency rates) | replace id tie-breaks with `rowid`; copy rows in ascending old id order; add a test asserting tie-break order is unchanged after migration |
| CSV import tag mis-assignment | attach tags by inserted id (§3.5) |
| Users restoring new backups on old versions | release-note warning; restore already reports a clear failure |
| Duplicate-merge behaviour changes for uuid backups | explicit test for the "DB at X, backup at Y" workflow |
| Performance of `INSERT OR IGNORE` for uuid imports | primary key index makes it O(1) per row, i.e. strictly better than today's O(n·m) |

## 7. Acceptance criteria

- [ ] Fresh install creates `records.id TEXT PRIMARY KEY` (schema v34) and the four triggers.
- [ ] Upgrading a v33 database keeps record count, tag associations, category usage counters and insertion order; ids are unique uuids.
- [ ] Creating, editing, duplicating, deleting, moving, transferring, filtering by wallet/profile, budgets, statistics, home widget and PDF/CSV export all behave as before.
- [ ] A backup containing two identical records restores both, with the correct balance, and each keeps its own tags.
- [ ] Importing the same uuid backup twice adds no records.
- [ ] Importing a uuid backup over newer data skips exactly the records whose ids already exist and inserts the rest.
- [ ] A 1.16.x backup still restores with the previous semantics (one-to-one content dedupe for repeat imports).
- [ ] No `int` record ids remain in `lib/` (`grep` in the PR description).
- [ ] `flutter analyze` clean; full `flutter test` green.

## 8. Rollback

* Before release: revert the branch — no data has been migrated in the wild.
* After release: no downgrade path (§5). If the migration misbehaves in the field,
  the fix must ship forward as a new migration (v35) that repairs ids/tags, plus
  guidance to restore the automatic database copy
  (`oinkoin_database.db`, see `BackupService.DATABASE_SNAPSHOT_FILE`) taken
  before the upgrade.

## 9. Open questions

1. Legacy backups: keep the 1.16.2 one-to-one content check, or insert everything
   and accept duplicates when the same legacy backup is imported twice? (The plan
   assumes keeping it.)
2. Do we add an explicit `created_at` column for ordering/auditing, or is the
   hidden `rowid` enough? (`rowid` is enough for the two current tie-breaks, but
   is not exportable.)
3. Should the same treatment be applied to `wallets` next (name-based matching on
   restore is the analogous weakness)?
4. Do we want deterministic (uuid v5 from content) ids for **legacy** imports so
   that re-importing the same legacy file is idempotent? Note it reintroduces the
   #452 collision for identical twins, so it would still need the counter-based
   matching for those.
